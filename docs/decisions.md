## D-01 クエストアプリとは別のリポジトリにする

- **状況**：チャットをアプリの中に作るか、外のAPIにするかを決める必要があった。
- **決めたこと**：AIを呼ぶ部分は別リポジトリのAPIにする。アプリに足すのはチャット画面だけ。
- **理由**
  - アプリは静的出力で、サーバー側の処理を持たない。APIキーをアプリに書くとブラウザから読めてしまう。
  - アプリは別のサイトに組み込まれる可能性がある。APIを独立させておけば、組み込み先からも同じものを呼べる。
  - アプリの公開手順（ZIP作成 → 本番反映 → 確認）を触らずに、チャット側だけ何度も更新できる。
- **選ばなかった案**：アプリの既存 Worker（集計用）に `/api/chat` を足す。部品は減るが、組み込みのときに切り出す作業が出る。
- **引き受ける手間**：呼び出し元の許可設定が要る。管理する場所が2つになる。

## D-02 Python + FastAPI を Cloudflare Workers で動かす。Uvicorn は手元だけ

- **状況**：本人の案は「Python の FastAPI を Uvicorn で動かし、サーバーは Cloudflare」。調べたところ、Cloudflare Workers は FastAPI に公式対応しているが、Workers の中に ASGI サーバーが入っており、本番では Uvicorn を使わない。
- **決めたこと**：FastAPI を Cloudflare Workers で動かす。Uvicorn は手元の開発とテストで使う。
- **理由**
  - アプリと同じ Cloudflare のアカウントで完結し、D1 にそのままつなげる。
  - Python と FastAPI は、AIを使うAPIでよく使われる組み合わせ。入力の形の確認（Pydantic）が最初から付いてくる。
  - FastAPI 本体を手元（Uvicorn）と本番（Workers）で同じにできるので、テストがしやすい。
- **選ばなかった案**
  - TypeScript の Worker：Cloudflare でいちばん実績があり、起動も速い。ただし本人が Python で作りたい。
  - 別のサーバーで FastAPI + Uvicorn：Uvicorn をそのまま本番で使えるが、Cloudflare の外に管理する場所が増える。
- **不確かな点**：ストリーミング、Anthropic の SDK、起動時間の3点は未検証（設計書 2章）。通らなければ Cloudflare Containers か TypeScript に切り替える。
- **見直す条件**：技術検証の結果が出たとき。

## D-03 データベースは Cloudflare D1。アプリの集計用とは分ける

- **状況**：質問を溜める場所が要る。本人の案は「SQL のデータベース」。
- **決めたこと**：Cloudflare D1（中身は SQLite、SQL で操作する）を使う。アプリがすでに使っている集計用データベースとは別に作る。
- **理由**
  - 溜めるのは表2つで、複雑な検索はしない。SQLite で足りる。
  - Workers からそのまま使え、別のサーバーを立てなくてよい。
  - 手元では SQLite のファイルで同じ SQL を試せる。
  - アプリの集計用と分けておけば、組み込みでアプリがなくなってもチャットの記録は残る。
- **選ばなかった案**：PostgreSQL（Supabase など）。組み込み先が使っているなら合わせる価値があるが、組み込み先の技術はまだ分からない。
- **見直す条件**：組み込み先のデータベースが分かったとき。

## D-04 ベクトル検索を入れず、目次から選ぶ2段階にする

- **状況**：質問に関係する資料だけをAIに読ませたい。毎回全部を読ませると高く、遅い。
- **決めたこと**：資料を話題ごとのかたまりに分けて目次を作る。1回目のAI呼び出しで目次から読むかたまりを選ばせ、2回目でその本文をもとに答えを書かせる。
- **理由**
  - 資料は文章として約6.9万字（講義ノート17件、用語116件、問題270問。2026-11-15 に実測）。目次は数千字に収まる見込みで、AIが一度に見渡せる量である（段階1で実際の長さを確かめる）。
  - ベクトル検索は、専用のデータベースと、資料を数値に変える処理が要る。1人で作るには部品が増える。
  - 利用者は用語を知らない言い方で聞く（「黒い画面」＝ターミナル）。目次を見て選ばせる方式は、言い換えに強い。
  - 1回目で「クエストと関係ない質問」も判定でき、2回目を呼ばずに済む。
- **選ばなかった案**
  - ベクトル検索：資料が何倍にも増えたら必要になる。
  - 全部を毎回読ませる：作りはいちばん単純だが、1問あたりの料金と待ち時間が大きい。
- **引き受ける手間**：AIを2回呼ぶので、1回分の待ち時間が足される。状態の表示で待ちを見せる。
- **見直す条件**：目次が一度に見渡せない量になったとき、または評価用の質問集で資料選びの間違いが目立つとき。`retrieve.py` だけを差し替える。

## D-05 用語はAIに選ばせず、文字の一致で拾う

- **状況**：用語ノートは116件ある。全部を目次に載せると、目次がほぼ倍の長さになる。
- **決めたこと**：質問文に出てくる用語を文字の一致で拾い、その説明を答えの材料に足す。目次には載せない。
- **理由**：用語は名前がはっきりしており、文字の一致で十分に拾える。AIを使わないので速く、料金もかからない。
- **弱いところ**：言い換え（「黒い画面」）は拾えない。そこは D-04 の目次選びで補う。
- **見直す条件**：用語の質問で答えが外れることが多いとき。

## D-06 質問は匿名で記録し、会話と答えの本文はサーバーに保存しない

- **状況**：つまずきを知るために質問を溜めたい。一方でアプリには「個人の回答履歴をクラウドへ送らない」という方針がある。
- **決めたこと**
  - 質問文は、誰のものかを記録せずに1問ずつ保存する。名前・ID・IPアドレスは保存しない。
  - 会話の続きはブラウザ内だけに持つ。答えの本文は保存しない。
  - APIキー・メールアドレス・PCのユーザー名らしき文字は、保存前に伏せ字にする。
  - チャット画面に、匿名で記録することを表示する。
- **理由**
  - アプリはすでに、用語ノートで見つからなかった検索語を同じ形（誰のものか記録しない）で溜めている。同じ考え方を延長する。
  - 想定する利用者はPCに慣れておらず、エラー文と一緒にAPIキーを貼ってしまうことがありうる。
  - 質問・選ばれた資料・資料の版があれば、答えはあとから作り直して確かめられる。
- **選ばなかった案**：ブラウザのIDと結びつけて保存する。同じ人が何度つまずいたかが分かるが、方針に反する。
- **残る確認**：匿名で記録すること自体への本人の了承（要件 Q-1）。

## D-07 資料の元はアプリ1か所。公開ファイル経由でAPIに渡す

- **状況**：講義の内容はアプリの `src/data/` にある。APIは別リポジトリなので、そのままでは読めない。
- **決めたこと**：アプリのビルド時に資料まとめファイル（`chat-content.json`）を作って公開サイトに置き、APIがそれを読み込む。
- **理由**
  - 資料を2か所に持つと、片方だけ直して食い違う。
  - 講義を取り込んでアプリを公開するだけで、チャットの知識も更新される。
  - 組み込み後に、コンテンツの足し方が変わっても、同じ形のファイルを出力すればAPIは変えずに済む。
- **選ばなかった案**：API側のリポジトリに資料を写しておく。アプリを触らずに済むが、更新のたびに写す作業が要る。
- **引き受けること**：アプリ側にスクリプトを1つ足す。ファイルは誰でも読めるが、中身はすでにアプリで公開されている内容だけ。

## D-08 判断専用モデル（Jev）は今は使わず、差し替え口だけ用意する

- **状況**：資料を選ぶ処理に、判断専用の速くて安いモデル（Jev）を使う案があった。
- **決めたこと**：最初は使わない。資料を選ぶ処理を1つのファイル（`retrieve.py`）に分け、あとで差し替えて比べられるようにする。
- **理由**
  - Jev は文章を書けないので、使えるのは資料選びと判定だけ。答えを書く側には別のAIが要る。
  - 2026年9月に早期アクセスが始まったばかりで、すぐ使えるか、日本語の資料でどのくらい正しく選べるかが分からない。
  - 利用者が少ないうちは、速さと料金の差が小さい。
- **見直す条件**：質問数が増えて資料選びの待ち時間や料金が効いてきたとき。評価用の質問集で比べてから決める。

## D-09 「いまの画面」をアプリが自動で質問に添える

- **状況**：想定する利用者は、自分がどの回の何をしているかを言葉で説明するのが難しい。
- **決めたこと**：アプリが、開いている期・回・画面の種類・解いている問題のIDを質問と一緒に送る。
- **理由**
  - 「Claude に直接聞くより速い」を実現する中心の仕組み。状況の説明が要らなくなる。
  - 資料選びの手がかりになり、選び間違いが減る。
- **引き受けること**：アプリとAPIの間に決まりごと（送る項目）ができる。項目はどれも任意にし、組み込み先から呼ぶときに無くても動くようにする。

## D-10 答えは順に届く形（ストリーミング）で返す

- **状況**：AIを2回呼ぶので、答えが全部できるまで待たせると数秒〜十数秒かかる。
- **決めたこと**：答えをできた順に画面へ流す。その前に「資料を探しています」などの状態も送る。
- **理由**：待ち時間の合計は同じでも、すぐ文字が出始めれば止まって見えない。「速い」と感じるかどうかは最初の文字までの時間で決まる。
- **不確かな点**：Workers 上の FastAPI でできるかは未検証（設計書 V-1）。できなければ全部作ってから返し、待ち表示で補う。

## D-11 ログインは作らない

- **状況**：利用者ごとの回数制限や履歴を正確にやるには、ログインが要る。
- **決めたこと**：最初はログインなしで、誰でも匿名で使える形にする。
- **理由**
  - アプリ自体にログインがなく、チャットだけに付けると使い始めの手間が増える。
  - 組み込み先にログインがあれば、そちらに合わせる方が二度手間にならない。
- **引き受けること**：回数制限はおおよそになる（ブラウザや回線を変えれば超えられる）。全体の1日上限と月の上限額で、料金の最悪の場合を止める。
- **見直す条件**：組み込み先のログインの仕組みが分かったとき。

## D-12 AIは Claude Haiku 5.5 で始める（資料選びも回答も）

- **状況**：どのAIを使うかを決める必要があった。候補は Claude Haiku 5.5、Claude Sonnet 5.5、OpenAI の最安モデル。
- **決めたこと**：資料選びも回答も Claude Haiku 5.5 で始める（2026-11-15、本人が決定）。
- **理由**
  - 仕事の中身は「渡された資料から答えを探して、分かりやすく言い直す」ことで、上位モデルの強みがあまり活きない。
  - このチャットの価値は速さにある。小さいモデルほど最初の文字が早く出る。
  - 見積もりで1回約0.4円（1,000円で約2,000回）。回数制限をゆるめにできる。
  - 資料選びと回答を同じ会社のAIにそろえると、APIキーと呼び出し方が1つで済む。
- **選ばなかった案**
  - Claude Sonnet 5.5：回答に使うと1回あたりが約13倍になる。
  - OpenAI の最安モデル：外部サイトの料金表では Haiku 5.5 と同額で、料金を理由に替える必要がない（公式の料金ページでは未確認）。
- **不確かな点**：料金は見積もりで実測ではない。答えの質は評価用の質問集でまだ確かめていない。
- **見直す条件**：評価用の質問集で「資料にないことを付け足す」「複数のかたまりをまたぐ質問で間違える」「あいまいな言い方を取り違える」が目立つとき。回答の側だけ Sonnet 5.5 に上げる。AIの呼び出しは `llm.py` に分けてあるので、他のモデルと同じ質問集で比べられる。

## D-13 月の上限額は2,000円。全体の上限は1日150問にする

- **状況**：利用者のチャットは質問のたびにAPI料金がかかる。使われすぎや攻撃で料金が跳ねないよう、上限を決める必要があった。
- **決めたこと**：月の上限額を2,000円にする（2026-11-15、本人が決定）。全体の1日の上限は、当初の仮の値500問から150問に下げる。
- **理由**
  - 1日500問のままだと、毎日上限まで使われた場合に月約6,400円になり、2,000円を超える。
  - 見積もりの1問約0.4円で逆算すると、月2,000円は約5,000問、1日あたり約166問。余裕を見て150問にする（150問 × 0.4円 × 30日 ＝ 約1,800円）。
  - 1日の上限を超えても、Claude API 側の月の上限額で必ず止まる。守りを二重にする。
- **引き受けること**：受講生が多い日に、上限に達して断ることがありうる。
- **不確かな点**：1問約0.4円は見積もりで、実測ではない。
- **見直す条件**：公開後に1問あたりの料金を測ったとき。上限に達して断った日が出たとき。

## D-14 「役に立った」ボタンの割合を成功の基準にしない

- **状況**：当初は「役に立ったが押された割合70%以上」を成功の基準に置いていた。
- **決めたこと**：ボタンは残すが、目標の数字は置かない（2026-11-15、本人の指摘で変更）。代わりに「資料にはありませんで終わった質問の割合 20%以下（仮）」を基準にする。
- **理由**
  - ほとんどの人は評価のボタンを押さない。押すのは強く満足したか不満だった人に偏り、割合は全体を表さない。
  - 「資料にはありません」の割合は、利用者が何もしなくても全部の質問で記録され、資料に何を足すべきかも分かる。
- **ボタンの使い道**：「立たなかった」が押された質問は全件読み、資料や指示文を直す材料にする。
- **見直す条件**：ボタンが十分な数押されるようになったとき。

## D-15 用意した質問と答えを先に見せ、AIは最後の手段にする

- **状況**：当初は「質問を送るとAIが答える」が中心で、よくある質問はボタンで2〜3個出すだけの補助だった。月の上限額を2,000円に決めたことで、AIを呼ぶ回数を減らす必要も出た。
- **決めたこと**（2026-11-15、本人が決定）
  - 講義を取り込むたびに、予想質問と答えをたくさん作り、承認したものを登録する。
  - チャット画面の端に「〜の質問」の一覧を置き、そこから選べるようにする。選ぶと用意した答えがその場で出る。
  - 一覧にない、または読んでも分からないときに、AIに聞く。
  - 自分の言葉で送った質問が、用意した質問と同じ中身なら、用意した答えを返す。
- **理由**
  - 用意した答えは事前に人が読んで承認するので、作り話が混ざらない。
  - 表示に通信もAIも要らないので、一瞬で出る。「Claude に聞くより速い」という目的にいちばん合う。
  - 料金がかからない。AIに進む質問が減るぶん、同じ2,000円で1日の上限を上げられる。
  - 想定する利用者は、何と聞けばいいか分からないことが多い。一覧を見ることが、質問の言葉を知る助けになる。
  - 下書きはサブスクの Claude で作れるので、作る側にもAPI料金がかからない。
- **選ばなかった案**

## D-23 守りと記録の作り方（伏せ字の範囲、回数の数え方、手元と本番のデータベースの切り替え）

段階3で決めたこと。2026-11-16、Claude Code の提案。本人の確認待ち。

- **決めたこと**
  1. **伏せ字の範囲**：次の4種類を伏せる。置き換える文字は `[伏せ字:キー]`・`[伏せ字:メール]`・`[伏せ字:名前]`。
     - 名前で秘密だと分かるもの（`API_KEY=…`、`password: …`、`パスワード：…` など）の値。
     - 形で分かるキー（`sk-…`、GitHub、AWS、Google、Slack、JWT）。
     - 英字と数字が混ざった32文字以上の続き（種類は分からないが、キーらしいもの）。
     - メールアドレスと、`/Users/名前/`・`/home/名前/`・`C:\Users\名前\` の名前部分。
  2. **回数の数え方**：先に1足してから、上限と比べる。ブラウザごとの回数 → 全体の回数、の順。足すのは SQL の1文（`INSERT … ON CONFLICT … DO UPDATE SET n = n + 1 RETURNING n`）。
  3. **ブラウザのIDの変え方**：`日付:ID` を SHA-256 にかける。日付を混ぜるので、同じブラウザでも日が変わると別の値になる。
  4. **前日の回数を消すタイミング**：その日の最初の質問のとき。
  5. **データベースの切り替え**：`store.py` に「書き込む（`run`）」「最初の1行を読む（`first`）」の2つだけを持つ入れ物を2種類（手元の SQLite 用、本番の D1 用）置く。SQL は共通。
  6. **空の値の書き方**：値が空の列は、INSERT の列に入れない（表の側で空になる）。
  7. **断り方**：`{"error": "種類", "message": "画面に出す文言"}` の形で返す。形が違う入力は、FastAPI の標準の 422 ではなく 400 にする（設計書 5.4）。送られた中身は返事に含めない。
  8. **呼び出し元の確認**：`Origin` が `ALLOWED_ORIGINS` にないとき、`Origin` がないときは 403。入力の形の確認より先に行う。許可したサイトには、断るときの返事にも CORS の見出しを付ける。
  9. **緊急停止**：`CHAT_ENABLED` が `false` のとき、数えも記録もせずに 503（メンテナンス中）を返す。
  10. **`POST /api/chat` を「AIを呼ぶ手前まで」つないだ**：呼び出し元 → 緊急停止 → 形 → 伏せ字 → 回数 → 記録、まで動く。AIの部分がまだないので、最後は 503（いまは答えられません）を返し、記録の `result` は `error` になる。段階4で、ここに資料選びと回答を入れる。
  11. **`POST /api/chat/feedback` を作った**：記録がなければ 404。
- **理由**
  - 1：想定する利用者は、エラー文や `.env` の中身をそのまま貼ることがある。名前で分かるものと、形で分かるものの両方を拾う。32文字以上の続きは、ハッシュ値やIDも消してしまうが、質問の意味はほぼ変わらないので、漏らさないほうを優先した。
  - 2：「読んでから書く」にすると、同時の質問で数がずれる。先に足せば、ずれない。
  - 3：質問の記録と結びつけないだけでなく、日をまたいで同じブラウザを追えないようにする。秘密の値（ソルト）を別に管理しなくて済む。
  - 5：SQLite と D1 は中身が同じなので、SQL を書き分ける必要がない。違うのは呼び出し方だけで、それを2つのクラスに閉じ込めれば、ほかのファイルはどちらで動いているかを知らなくてよい。
  - 6：Python の「空」（`None`）を D1 に渡すと、JavaScript 側で扱いが変わるおそれがある。渡さない形にして避けた。
  - 8：断る返事に CORS の見出しがないと、ブラウザは状態コードも文言も読めず、画面に理由を出せない。
- **引き受けること**
  - 断られた質問でも、ブラウザごとの回数は増え続ける（10を超えても足す）。上限の判定には影響しない。
  - 全体の上限で断られた質問は、ブラウザの回数を1つ使う。
  - AIの呼び出しが失敗した質問も、回数を1つ使う（料金を守るため、AIを呼ぶ前に数える）。
  - 伏せ字は形を見ているだけなので、短いパスワードを文の中にそのまま書かれた場合などは拾えない。画面の注意書き（「APIキーやパスワードは貼らないでください」）と合わせて守る。
- **動かして確かめたこと**（手元。公開した状態では確かめていない）
  - 自動テスト96件が通る（資料14、守りと形46、記録と回数18、APIの決まり18）。
  - `pywrangler dev` と手元の D1 で、次を確かめた。
    - 許可していないサイト・`Origin` なし → 403。形が違う → 400。事前確認（OPTIONS）→ 204 と CORS の見出し。
    - 伏せ字にした質問文が D1 に保存される（`/Users/[伏せ字:名前]/app で ANTHROPIC_API_KEY=[伏せ字:キー] …`）。日本語は文字化けなし。空の列は空として読める。
